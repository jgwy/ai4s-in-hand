# 第 14 章：AI 辅助计算研究

> [!CAUTION]
> 本章是可公开审阅的 Alpha 初稿。AI 生成的代码一律视为未经信任的外部贡献：先定义科学验收与测试，再在隔离环境运行，最后由人类研究者决定是否接受。

AI 可以很快写出数据清洗、建模和绘图代码，也可以很快把单位混掉、泄漏测试集或静默跳过缺失值。计算研究的可信边界不在“代码能运行”，而在输入、变换、数值假设、测试与主张之间是否存在可追踪关系。

## 本章解决的问题

完成本章后，你应该能够：

1. 在生成实现之前写出科学验收标准和测试；
2. 区分单元测试、性质测试、回归测试与科学有效性检查；
3. 审查 AI 代码中的单位、数据泄漏、随机性、数值稳定性和异常处理；
4. 保存数据、环境、配置、代码、运行与人工修改的 provenance；
5. 用固定脚本或人工计算作为独立基线；
6. 只接受通过测试且没有越过主张边界的生成代码。

## 核心概念

### 14.1 先写“什么算对”

把第 13 章的判别实验翻译成验收合同：

| 层级 | 示例验收条件 | 失败后动作 |
| --- | --- | --- |
| 输入 | 候选 ID 唯一；单位、范围和缺失规则明确 | 拒绝运行，不静默修补 |
| 变换 | 划分只由训练元数据决定；测试标签不可见 | 标记泄漏，重建全流程 |
| 算法 | 同预算、同初始化；随机种子来自配置 | 结果作废并记录偏离 |
| 数值 | 小型手算样例一致；无 NaN/Inf；边界条件满足 | 隔离最小失败输入 |
| 科学 | 同时报预测误差、物理/约束残差和适用域 | 缩小主张，不用单一分数掩盖 |

只有验收合同冻结后，才让 AI 生成函数。否则生成器也会隐式决定研究问题。

### 14.2 四类测试各自回答什么

- **单元测试：**一个函数在已知输入下是否给出预期输出；
- **性质测试：**对一类输入，不变量是否始终成立，如排序不改变 best-so-far；
- **回归测试：**修订代码后，已确认的小型结果是否意外变化；
- **科学有效性检查：**实现即使正确，数据与设计是否足以支持主张。

测试 oracle 应尽量独立于被测实现。用 AI 同时写函数和复制其逻辑写测试，两个文件可能共享同一错误。优先使用手算样例、解析解、成熟库的窄接口或另一种简单实现。

### 14.3 生成代码的接受协议

```text
问题与判据冻结
      ↓
人工写最小失败测试 ──→ 固定脚本/手算 oracle
      ↓
AI 生成最小实现（不接触密钥、生产数据或设备）
      ↓
静态审查 → 隔离运行 → 测试 → 小数据科学审查
      ↓
接受 / 修改并重测 / 拒绝并记录
```

接受记录至少包含模型或工具名称、核验日期、输入提示的功能摘要、生成文件、人工修改、测试结果和责任人。不需要公开包含敏感上下文的完整提示，但必须披露 AI 的实质性作用。

### 14.4 provenance 是结果的一部分

一次运行 $r$ 可表示为：

$$
r=(D,V_D,E,C,V_C,S,H,O),
$$

其中 $D$ 是数据，$V_D$ 是数据版本或校验值，$E$ 是环境，$C$ 是配置，$V_C$ 是代码版本或工作树标识，$S$ 是随机种子，$H$ 是硬件，$O$ 是输出。还要记录人工中断、重跑理由和失败日志。

National Academies 将“同数据、同计算步骤与条件得到一致计算结果”归入计算可复现性；它与用新数据独立重复科学发现不是同一要求（[NASEM, 2019](https://doi.org/10.17226/25303)）。

### 14.5 Research Agent 仍受同一验收约束

Agent 可以调用文件、解释器、模拟器和绘图工具，但工具调用成功只说明执行层工作。权限应最小化：默认只读输入，输出写到新的运行目录，网络与外部 API 按需开放，不允许自动覆盖原始数据。任何改变数据定义、主要指标或停止条件的动作都需要人工确认并进入日志。

## 可检查产物：测试先行的最小计算包

### 14.6 小型任务：检查序贯筛选轨迹

输入为 `candidate_id, step, observed_value`，目标是计算固定预算下的 best-so-far 轨迹与首次达到阈值的步数。先写以下测试，再生成实现：

```python
def test_best_so_far_known_case():
    values = [0.2, 0.1, 0.5, 0.4]
    assert best_so_far(values) == [0.2, 0.2, 0.5, 0.5]

def test_prefix_invariance():
    values = [0.2, 0.1, 0.5]
    assert best_so_far(values[:2]) == best_so_far(values)[:2]

def test_rejects_nonfinite_values():
    with pytest.raises(ValueError):
        best_so_far([0.2, float("nan")])
```

科学验收再增加：同一方法不能重复查询候选；所有方法预算相同；阈值在看测试轨迹前固定；失败运行计入失败次数而不是删除。

### 14.7 推荐目录与运行记录

```text
compute-package/
├── README.md              # 问题、命令、预期范围与限制
├── environment.yml        # 或固定的 requirements
├── config/default.yaml    # 预算、阈值、种子
├── src/metrics.py
├── tests/test_metrics.py
├── data/README.md         # 来源、版本、许可证、校验值
├── runs/<run-id>/         # 配置快照、日志、指标、失败
└── report/claim-map.csv   # 输出到主张的映射
```

核心路径用 CPU 和小型静态数据完成。若外部服务不可用，测试与固定样例仍必须运行；不要把在线 API 变成隐含前提。

### 14.8 简单基线

用电子表格累计最大值，或用不足十行、经过人工逐行检查的固定脚本计算同一轨迹。这一基线用于发现排序方向、索引和阈值的错误。复杂的 Agent 工作流只有在减少人工时间的同时，通过同一套预先冻结的测试与独立 oracle，并且不降低覆盖范围、容差、验收条件或 provenance，才显示出相对基线的价值。

“Good enough practices”建议把数据、软件、协作与项目组织纳入日常计算研究（[Wilson et al., 2017](https://doi.org/10.1371/journal.pcbi.1005510)）；研究软件的健壮性还要求可配置输入、明确版本和自动测试，而不是只在作者机器上运行（[Taschuk & Wilson, 2017](https://doi.org/10.1371/journal.pcbi.1005412)）。

## 常见错误与失败模式

| 现象 | 根因 | 诊断与修复 | 不能推出 |
| --- | --- | --- | --- |
| 代码运行但结论反了 | 最小化/最大化方向或单位错误 | 手算样例与量纲检查 | 无报错即正确 |
| 测试全部通过却泄漏 | 测试只覆盖函数，不覆盖数据流程 | 对划分、拟合边界和标签访问加测试 | 软件正确即科学有效 |
| AI 写的测试重复实现 | 函数与 oracle 共用逻辑 | 独立手算、解析解或第二实现 | 双方一致即真值 |
| 重跑结果无法解释 | 环境、数据或种子未保存 | 每次运行冻结配置和校验值 | 固定一个种子即稳定 |
| 异常样本被静默删除 | 生成代码追求成功路径 | 默认失败并记录显式过滤理由 | 干净结果代表原数据 |
| Agent 自动改主要指标 | 权限和审批边界缺失 | 指标冻结；变更需人工闸门 | 自动优化即客观研究 |

## 科学有效性与证据检查

- [ ] 测试是否先于生成实现，且至少一个 oracle 独立于 AI？
- [ ] 是否覆盖单位、缺失、重复、非有限值、边界与排序方向？
- [ ] 数据划分和预处理是否只拟合训练数据？
- [ ] 所有比较是否共享数据、预算、初始化和指标？
- [ ] 是否保存环境、配置、种子、硬件、日志、失败与人工修改？
- [ ] 输出是否映射到限定主张，而非由图形外观直接推断机制？
- [ ] 网络/API/GPU 不可用时是否有固定脚本或静态样例？
- [ ] AI 代码是否经过最小权限、隔离运行和人工接受？

## 练习与评价要点

1. **概念辨析：**说明测试通过、数值正确、计算可复现和科学结论成立之间的关系。评价要点：四者逐层增加责任，不能互相替代。
2. **失败诊断：**一段代码先对全数据标准化再划分。评价要点：识别泄漏、改为训练集拟合、加回归测试并作废旧结果。
3. **迁移实践：**为阻尼振子代理写解析解小样例、单位测试和外推检查。评价要点：初始条件、时间范围、状态误差与动力学残差齐全。
4. **AI 接受审计：**审查一段生成代码并填写接受/拒绝记录。评价要点：引用具体测试证据、人工修改和未解决风险，不使用“看起来正确”。

## 本章小结与下一步

AI 代码只有在独立 oracle、测试、隔离运行和科学验收之后，才从候选文本变成可使用的研究软件。下一章把这个计算包放入虚拟高通量流水线，继续区分批量执行、自动化与根据反馈决策的自驱动实验室。
